Pipeline de Recolha de Dados & Integração

Para criares um dataset e posteriormente executares a inferência, deves garantir que a amostragem é determinística. Conforme abordado nas sebentas de "Timers and Interrupts" do MICSA, usar temporizadores de hardware (Timers) é muito superior a usar delays (Polling) para sinais biométricos/físicos.

Estratégia de Amostragem (Software Integration)

  • Frequência de Amostragem Ideal: Para gestos humanos (movimentos lentos), 50Hz a 100Hz é o padrão da indústria. O teorema de Nyquist sugere que 50Hz capta dinâmicas até 25Hz, o que é suficiente para o movimento da mão.
  • Estrutura: Configura um Timer (ex: TIM2) para gerar uma interrupção a cada 20ms (50Hz). Na rotina de interrupção (ISR), define uma flag. No main loop, se a flag estiver ativa, lê o ADC (dedos) e o I2C (IMU), limpa a flag, processa os dados e envia.
// FASE 1: Imprimir RAW Data via UART para o PC (Para treinar o modelo) // Formato CSV ideal para o Edge Impulse Data Forwarder void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim) { if (htim->Instance == TIM2) { data_ready_flag = 1; } } int main(void) { // Inicializações (HAL, SystemClock, GPIO, ADC, I2C, TIM2, UART) HAL_TIM_Base_Start_IT(&htim2); // Start Timer Interrupt @ 50Hz while (1) { if (data_ready_flag) { data_ready_flag = 0; // Lê IMU (I2C) MPU6050_Read_All(&i2c1, &MPU6050); // Lê 5 sensores de flexão (ADC c/ DMA ou Polling rápido) read_ADC_channels(flex_data); // Imprime em formato CSV via UART char buffer[128]; sprintf(buffer, "%d,%d,%d,%d,%d,%d,%d,%d,%d,%d,%d\r\n", MPU6050.Ax, MPU6050.Ay, MPU6050.Az, MPU6050.Gx, MPU6050.Gy, MPU6050.Gz, flex_data[0], flex_data[1], flex_data[2], flex_data[3], flex_data[4]); HAL_UART_Transmit(&huart2, (uint8_t*)buffer, strlen(buffer), HAL_MAX_DELAY); } } }

Comparativo de Frameworks TinyML

Para hardware específico como o STM32F411RE (ARM Cortex-M4F, 512KB Flash, 128KB RAM), existem 3 vias principais. A escolha depende da vossa familiaridade com Machine Learning vs. Engenharia de Sistemas Embebidos.

🥇 Edge Impulse

O Melhor para Estudantes. Plataforma web End-to-End. Usa a ferramenta Data Forwarder para ler a UART do STM32, treina o modelo na nuvem e exporta uma biblioteca C++ pura. O F411RE tem memória suficiente para os modelos que o EI gera (Random Forest ou pequenas NNs).

🥈 X-CUBE-AI (ST)

A Melhor Otimização. É o plugin nativo do STM32CubeIDE. Implica que já tenhas um modelo treinado (Keras, TFLite). Ele converte e comprime o modelo de forma extrema para a RAM/Flash do STM32. Requer que faças a pipeline de treino em Python no teu PC primeiro.

🥉 TFLite Micro

O "Engine" Core. Implementar TFLM diretamente a partir do zero no STM32 em C++ é muito trabalhoso. O Edge Impulse e o X-CUBE-AI já usam os kernels do TFLM ou CMSIS-NN por baixo, poupando-te semanas de configuração de Makefiles e dependências.

Apresentação: Stack Web Local

Para apresentar a "tradução" da luva no ecrã em tempo real, precisas de algo que leia a porta COM (UART/Bluetooth) do teu PC e envie isso para uma interface Web (HTML/JS).

🟩

Recomendação Principal: Node.js + SerialPort + Socket.io

É a abordagem mais robusta e "real-time". Um script Node.js usa a biblioteca serialport para ler os dados que chegam via Bluetooth HC-05 (que no PC é visto como uma porta COM virtual). Assim que lê a string "GESTO:A", envia via WebSocket (socket.io) para o teu ficheiro HTML local, atualizando a DOM instantaneamente, sem refreshes de página.

🐍

Alternativa Simples: Python Flask + PySerial + AJAX

Se o teu grupo souber mais de Python, usa o pyserial para ler a porta COM. Cria uma rota Flask (ex: /gesto_atual) que retorna a última leitura em formato JSON. Na tua página HTML/JS, usas setInterval() e fetch() a cada 100ms para ir buscar a nova letra. É um pouco menos "real-time" que WebSockets, mas muito mais fácil de codificar inicialmente.

🌐

Experimental: Web Bluetooth API

Permite que o browser (Chrome) ligue diretamente ao Bluetooth sem nenhum servidor Node ou Python (HTML/JS puro). CUIDADO: Só funciona com módulos BLE (Bluetooth Low Energy) como o HC-08, JDY-08 ou ESP32. O HC-05 é Bluetooth Clássico e não é suportado nativamente pelo Chrome nesta API.

Desafios Clássicos e Soluções (Pesquisa Guiada)

Na montagem deste hardware/software, vão bater de frente com os seguintes problemas. Eis as palavras-chave e recursos que devem pesquisar para os resolver.

🚨 Ruído & Drift do MPU6050

Problema: Se usarem apenas os valores de giroscópio (graus/s) e fizerem integração matemática, o valor vai "voar" ao fim de poucos segundos (Drift).

Solução (Pesquisar): "Jeff Rowberg i2cdevlib MPU6050 DMP". O MPU6050 tem um processador interno (DMP) que funde o acelerómetro e o giroscópio automaticamente e cospe Quaternions limpos e Euler Angles.

🚨 Ruído dos Sensores de Flexão

Problema: Sensores resistivos sofrem de "jitter" analógico. O conversor A/D (ADC) do STM32 capta muita interferência eletromagnética (EMI).

Solução (Pesquisar): "STM32 ADC DMA Oversampling" ou implementar um filtro Moving Average (Média Móvel) de 5-10 amostras no C. Adicionar um condensador de 10nF em paralelo com a resistência de pull-down no hardware (Filtro Low-Pass RC).

🚨 Latência via UART/Bluetooth

Problema: Usar `printf` ou `HAL_UART_Transmit` em modo Polling atrasa o microcontrolador e estraga a frequência de amostragem (os 50Hz não se mantêm).

Solução (Pesquisar): "STM32 HAL UART Transmit DMA". Usar o canal DMA permite que o processador mande a String para a UART e continue o seu trabalho sem ter que esperar que os bits saiam pelo cabo.

🚨 Memória Ram do STM32F411

Problema: Redes Neuronais precisam de alocar buffers (Tensor Arena). Se o modelo for grande, dá HardFault Handler (crash).

Solução (Pesquisar): Usar "Edge Impulse EON Compiler" ou "CMSIS-NN". Isto reduz a RAM necessária ao evitar o interpretador TFLite, compilando a rede diretamente para código C bruto. Aumentem também o tamanho da Heap/Stack no ficheiro .ld no STM32CubeIDE.
